Reference design: recommender system

Scenario: a personalized home feed mixing followed topics, followed users and recommended content. Optimize useful engagement with freshness, diversity and negative-feedback guardrails. Start with popular/recent content before adding learned retrieval and ranking.

{{recommender}}

Retrieval and data

  • Candidate sources: combine two-tower ANN retrieval with follows, co-engagement and a fresh/cold-start pool. Allocate candidate budgets by marginal recall and latency. A strong ranker cannot recover an item never retrieved.
  • Embedding design: ID embeddings capture known preferences; text/image/metadata features help unseen items. Train query and item towers together, but precompute item embeddings. Deploy compatible query models and index versions together.
  • Negative sampling: in-batch negatives are cheap but popularity-skewed; random negatives are easy; hard negatives improve discrimination but may be unlabeled positives. Mix sources and inspect false negatives. Sampling-probability corrections such as log-Q require a justified sampling model, not a universal subtraction rule.
  • Training data: log impressions, positions, clicks, dwell and hides; unexposed items are not observed negative outcomes. Use point-in-time feature joins, temporal evaluation and checks for delayed labels. Nearline session features improve responsiveness but add consistency and freshness requirements.

Ranking and policy

  • One ranker or a cascade: start with one affordable ranker. Add a light stage to prune candidates when expensive cross-features or sequence models exceed the latency budget. Measure quality lost at each cutoff.
  • Loss: pointwise BCE learns click probabilities under the training distribution; it does not guarantee calibrated serving probabilities. Pairwise/listwise losses emphasize relative ordering. If combining click, dwell and hide predictions into expected value, validate calibration and objective weights separately.
  • Exposure bias: position features can encode the previous policy. Use randomized exposure where feasible, or propensity weighting with overlap assumptions and variance controls. A position-aware model needs an explicit serving convention; setting position to zero is not a universal correction.
  • Diversity and freshness: apply eligibility before ranking; use category/creator caps, freshness boosts or MMR-style relevance–similarity tradeoffs afterward. Tune for utility loss versus variety. Maintain a fresh-item source because post-ranking boosts cannot rescue missing candidates.

Serving, evaluation and failure paths

  • Feature-store placement: upstream stream/batch jobs compute features; the online store serves low-latency lookups and the offline store supports point-in-time training joins. Store definitions, timestamps and versions together. The feature store does not itself decide ranking.
  • Large catalogs: keep only hot serving features in memory, use a durable distributed store for the rest, fetch only retrieved candidates and batch requests. Choose partition keys and replication from access patterns; putting every item in Redis is not a requirement.
  • When to infer: precompute stable item features and embeddings; compute fast-changing user/session scores at request time. For predictable events, such as incoming messages, precompute suggestions on arrival when the freshness/compute tradeoff is favorable.
  • Exploration: cold-start metadata and onboarding preferences help before interaction history exists. A controlled exploration budget can collect new-item feedback; log exposure probabilities if later evaluation needs propensity correction.
  • Online/offline split: stream events into an online feature store and offline training data; retain consistent feature definitions. Training publishes models and ANN artifacts through versioned storage/registry. The recommendation service orchestrates retrieval, filtering, feature lookup, ranking and policy.
  • Cache and fallback: scope request caches to user/context and versions; invalidate or shorten TTL for rapidly changing interests. If a ranker or store fails, serve an eligible popular/recent pool. A Bloom filter may accelerate seen-item checks but can drop valid items through false positives; it is not an authoritative ACL check.
  • Measure: retrieval Recall@K, ranking NDCG, probability log loss/calibration, then online useful engagement or retention with hide-rate and latency guardrails. Segment new users/items. Inspect exposure feedback loops, stale features and logging failures before retraining after a regression.

Reference design: permission-aware RAG

Scenario: answer questions over versioned enterprise documents, with verifiable sources and tenant/user access control. Start with a fixed retrieve → rerank → generate pipeline; add iteration only for queries that benefit from it.

{{rag}}

Ingestion and chunking

  • Fixed versus structure-aware chunks: fixed token windows are simple; heading/paragraph-aware chunks preserve meaning. Small chunks improve retrieval precision but lose context; large chunks dilute matches and consume generation budget. Evaluate sizes on actual query types rather than choosing one universal length.
  • Overlap and parent context: modest overlap protects boundary facts but creates duplicates. Retrieve small child chunks, then expand to a bounded parent section when needed. Deduplicate overlapping evidence before generation.
  • Tables and metadata: preserve column headers, units, entity and reporting period with rows; avoid splitting a number from its meaning. Store document ID, span/page, version, timestamp and ACLs alongside each chunk. Citation IDs must resolve to the version used.
  • Updates and deletes: incremental content hashes reduce re-embedding. Version embeddings with the model and chunking policy. Track index lag; use authoritative revocation/deletion checks when stale indexes could expose removed content.

Retrieval and reranking

  • Lexical versus dense: BM25 handles exact names, identifiers and unusual terms; dense retrieval helps semantic paraphrases. Hybrid retrieval broadens coverage. Fuse rankings with reciprocal rank fusion or validated score normalization; raw scores from different retrievers are not inherently comparable.
  • Permission boundary: filter by tenant and ACL in retrieval where supported, and recheck authoritative eligibility before model context. Restrictive post-filtering can underfill top-k; fetch additional eligible candidates without allowing denied content into prompts or caches.
  • Reranker choice: a cross-encoder scores query–passage pairs jointly and often improves precision at extra cost. An LLM reranker can use richer instructions but adds latency, expense and variability. Rerank a bounded candidate set; compare quality gain against a no-reranker baseline.
  • Context packing: choose evidence under a token budget, remove redundant chunks, preserve source labels and leave output headroom. Select diverse evidence for multi-document questions; more retrieved text is not automatically better.

One-shot versus agentic retrieval

  • Fixed pipeline: best starting point for direct questions with a known corpus; predictable latency, cost and evaluation. A deterministic query rewrite or decomposition step may be enough without an open-ended agent.
  • Bounded iteration: use when the next search depends on discovered entities or missing evidence. Let the system inspect results, refine queries and retrieve again, with explicit limits on calls, elapsed time and tokens. Stop when evidence is sufficient or abstain when the budget is exhausted.
  • Routing: compare fixed and iterative paths on the same query set. Adopt agentic retrieval only where its incremental answer quality justifies extra latency and failure opportunities. Tool-using workflows that act on external systems belong in the next reference design.

Automatic evaluation scorecard

  • Retrieval: evidence Recall@K and ranked relevance; evaluate the final context packet as well as raw retrieval.
  • Groundedness: decompose answers into factual claims and check support in context. A supported claim can still be wrong if its source is outdated.
  • Correctness and completeness: compare against verified reference facts and the question’s required parts; use deterministic arithmetic/date checks when possible.
  • Citations: check source IDs and claim-to-cited-span support, plus coverage of claims needing citations.
  • Abstention: measure unsupported answers on insufficient-evidence cases separately from unnecessary refusals on answerable cases.
  • Trust the evaluator only after validation: calibrate narrow semantic judge rubrics against human labels; require evidence spans. Keep access failures as hard gates and cost/latency alongside quality. Run with gold context to distinguish retrieval failures from generation failures.

Grounding and operations

  • Answer contract: cite supporting passages, distinguish conflicting versions and abstain on insufficient evidence. Citation membership is necessary but does not prove a claim follows from the source; use evidence/entailment checks and human evaluation.
  • Security and fallback: treat retrieved instructions as untrusted data. Keep access checks outside the model; send fallback models only data permitted for that destination. Key caches by access scope, corpus and prompt/model versions.
  • Evaluation: separate retrieval recall, reranker quality and answer correctness/grounding. Include multi-hop, stale-document, no-answer and permission-denied cases. Monitor index freshness, p95 latency, token cost and access violations; canary changes to chunking, embeddings and prompts independently.

Reference design: agentic knowledge work

Scenario: research across documents, sheets and email, reconcile evidence, produce a report and optionally stage updates. Success is a correct deliverable or authorized final state, not a plausible conversation.

Request + identity → scope and route → bounded plan / tool loop → verify → preview writes → commit + audit

Workflow and autonomy

  • Fixed workflow first: use a prescribed sequence for repeatable tasks such as filling a report template. Use an agent loop when tool choice genuinely depends on intermediate results. Route simple questions to the RAG path.
  • State: persist task ID, plan, evidence references, tool results, pending actions and budget counters. Checkpoint around durable operations so a restart resumes safely. A model-generated plan is a proposal, not authorization.
  • Parallelism: batch independent reads to reduce serial latency; keep dependent calls ordered. Bound concurrency and handle partial failures. Add subagents only for separable subtasks whose outputs can be verified; coordination can cost more than it saves.
  • Termination: enforce step/time/token limits, detect repeated failed calls and return a partial result with missing evidence rather than loop indefinitely. Define when the user must resolve ambiguity.

Context, tools and memory

  • Progressive disclosure: fetch titles, schemas and summaries before full content. Pass large tables through authorized typed handles and request relevant rows/aggregates. Handles must enforce scope and lifetime; they are not permission bypasses.
  • Compaction: retain goals, constraints, evidence IDs, decisions and outstanding work. Summaries can lose details, so keep retrievable originals. Stable system/tool prefixes may improve prefix-cache reuse; do not freeze stale task facts merely for caching.
  • Memory tiers: current task state is distinct from project history and durable user facts. Store provenance, timestamps and deletion controls; retrieve only relevant authorized memory and resolve contradictions before using it.
  • Tools: expose narrow typed operations, validate arguments server-side and return actionable errors. Retry transient read failures within a budget. For writes, use idempotency keys and reconcile unknown outcomes before retrying.

Action safety and evaluation

  • Read versus write: scope connectors to the user, enforce ACLs for every call and isolate untrusted document/email content from authorization decisions. Stage consequential actions as a concrete preview; approval must bind to the exact action before execution.
  • Verification: check output schemas, spreadsheet formulas, citations and destination identities deterministically where possible. Verify the final state after writes and keep an audit trail. Prompt-injection filters alone do not create a security boundary.
  • Test worlds: seed consistent docs/sheets/emails with distractors, missing permissions and conflicting facts. Grade expected deliverables/state changes plus forbidden side effects, not a single prescribed tool sequence. Hold out world templates and compare with real task samples to detect synthetic overfitting.
  • Reliability: track single-run success, repeated-run consistency, cost, latency and unwanted actions. At-least-one success across several attempts is not the reliability of one user run. Calibrate subjective rubric judges against human labels and report disagreement.
  • Improve from failures: cluster traces into retrieval misses, incorrect arguments, context loss, premature completion and verification failures. Fix the dominant cause, compare on paired tasks and report uncertainty; do not promise a fixed lift. Route simple steps to smaller models only after quality checks, then canary and retain rollback versions.

Upgrading the model powering the agent

Goal: determine whether a new model improves task quality or lowers cost without introducing regressions.

  1. Build the evaluation set. Sample representative tasks with restorable initial state, plus a separate suite of known failures. Review thumbs-up, thumbs-down and unrated cases to discover failure modes; feedback is a signal, not ground truth.
  2. Define and validate the rubric. Combine task requirements with the failure taxonomy: completion, correctness/grounding, completeness, permitted actions and appropriate refusal. Use deterministic outcome checks where possible and LLM judges for semantic criteria. Validate graders against held-out human labels.
  3. Rerun asynchronously. A model-release event queues incumbent/candidate runs on the same tasks in isolated environments, followed by grading jobs. Freeze harness, data and grader versions. Let each model choose its own actions: replaying the old transcript cannot measure a changed trajectory. Sandbox writes, bound retries and distinguish infrastructure errors from agent failures.
  4. Compare quality and cost. Measure absolute rubric scores and blinded pairwise win/tie/loss, with repeated trials, uncertainty and important task slices. Count whole-task tokens, tools and retries; report cost per task and spend per successful task. Keep authorization failures as hard gates.
  5. Validate online before ramping. Offline gates earn a small canary, then a controlled A/B test with stable assignment and rollback. Track task completion, thumbs feedback and rating participation, edits/retries, latency and cost. Test the actual serving policy: best-of-N is only relevant if production also generates and selects among N attempts.
